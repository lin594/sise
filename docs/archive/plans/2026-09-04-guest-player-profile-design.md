# 免注册本机牌友档案设计

## 背景与目标

当前昵称和房间凭证已经保存在浏览器本机，但服务端不认识“同一台设备上的同一位牌友”。玩家每次换房都会获得新的房间身份，已完成局数和胡牌次数也不会跨桌保留。完整账号注册、密码找回和跨设备登录对现阶段过重，也会增加老年玩家第一次进入的门槛。

本轮增加一个免注册、无需记忆密码的临时牌友档案：浏览器首次使用时生成独立高熵凭证，服务端只按凭证保存昵称、已完成局数、胡牌次数和总得分。模式大厅用一行清楚文字展示档案；牌局、邀请链接和公开房间状态不展示凭证或额外统计。

## 方案比较

1. 只用 `localStorage` 累计。实现最轻，但玩家可直接伪造，服务重建与多标签页容易重复计数，也不能作为后续账号迁移的数据基础。
2. 立即实现正式账号。可以跨设备，但注册、密码、找回、隐私与运维范围过大，会破坏当前“一步进入”的体验。
3. 服务端匿名档案（采用）。客户端保存独立随机凭证，服务端在权威结算时记账；不要求注册，也为未来绑定正式账号保留迁移入口。

## 身份与隐私边界

- 客户端生成 `gp_` 加 48 位十六进制随机串，保存在 `sise_guest_profile_token_v1`。
- 档案凭证与每个房间的 `playerToken` 分离；前者跨房间，后者只恢复具体座位。
- 档案凭证通过 WebSocket 加入参数或 HTTP `Authorization: Bearer` 传输，不进入查询参数、邀请链接、Colyseus Schema、动作记录或服务端普通日志。
- 服务端只保存经过规范化的最近昵称、局数、胡牌次数、总得分和更新时间，不保存 IP、设备信息或手牌历史。
- 页面明确称为“本机临时档案”，说明清除浏览器数据后无法找回，不能伪装成正式账号。

## 服务端数据流

生产环境连接现有 Redis；开发或 Redis 不可用时使用进程内存实现，档案失败不得阻止开房或牌局。Redis 键使用档案凭证的 SHA-256 摘要，不把原始凭证写进键名。

`GET /guest-profile` 使用 Bearer 凭证读取档案；不存在时返回零局档案。`PUT /guest-profile` 更新规范化昵称并创建档案。这两个接口单独限流并返回 `Cache-Control: no-store`。

玩家加入房间时携带 `profileToken`。房间把它绑定到真人座位；好友房访客未选座前只保存在当前会话，选座后再绑定。每局权威 `round_result` 只结算一次，随后为每位真人异步记录一局：赢家的胡牌次数加一，每人的总得分加本局 `totalScore`。配置机器人没有档案，临时托管仍记在原真人档案上。存储失败只记录简短告警，不重复广播结算。

## 客户端体验

昵称确认时后台创建或更新档案，但网络失败不阻止玩家进入模式大厅。模式大厅显示：

> 本机临时档案 · 已玩 12 局 · 胡 3 局

零局时显示“还没有完成牌局”。档案加载中不展示骨架屏，避免页面跳动；不可用时保持原大厅。每次收到完整结算后刷新档案，确保数字来自服务端而非客户端自行推算。568×320 下档案行与标题同区，必要时隐藏辅助说明但保留局数和胡牌次数。

## 错误处理与兼容

- 旧浏览器首次升级自动生成档案凭证，现有昵称、房间 token 和显示设置不变。
- 非法档案凭证按匿名未绑定处理，不能影响加入房间；HTTP 档案接口返回通用中文错误。
- Redis 断开时自动降级到本进程内存；牌局始终优先于统计。
- 多次收到同一终局路径不会重复记账，因为房间现有 `ended` 守卫仍是唯一结算入口，档案层再按 `roomId + roundNumber + profile hash` 做幂等保护。

## 验收

- 新设备无需注册即可进入，模式大厅出现零局档案。
- 完成一局后局数加一；只有赢家胡牌次数加一；四家总得分仍由权威结算决定。
- 单人练习、快速配桌和好友同桌都可累计，机器人不创建档案，真人开启托管后仍累计。
- 刷新、换房和服务端重启后 Redis 档案仍可读取。
- 邀请 URL、本地 URL、公开 Schema 和日志中均没有 `profileToken`。
