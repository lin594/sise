# 声明阶段引导与焦点设计

## 背景

每局开场都需要确认亮鱼和暗坎。系统已经自动选择推荐方案，但 568×320 界面仍把主按钮写成“确认”，固定底栏又遮住了部分可调整内容；玩家看不到明显的滚动提示，容易误以为没有调整入口。声明弹层出现时也没有主动接管焦点或限制 Tab，键盘、开关控制和读屏用户可能停留在已经消失的大厅按钮上。

## 方案比较

- 把所有调整项塞进首屏：会迫使手牌和牌字继续缩小，不符合老年用户优先级。
- 默认折叠调整项：首屏更简单，但有鱼或暗坎时玩家难以直接核对系统选择，并增加展开状态复杂度。
- 保留可滚动详情，强化“一键开始”主路径、明确上滑提示，并补齐模态焦点管理：不牺牲牌面大小，也让需要调整的玩家知道下一步。

采用第三种。

## 文案与交互

- 无声明时主按钮显示“无需声明，开始游戏”。
- 有推荐或自选内容时显示“开始游戏 · 亮鱼 N 组 · 暗坎 N 个”，让按钮本身说明点击结果。
- 练习模式的极小屏底栏显示“上滑可调整 · 练习不限时”；其他尺寸继续显示“不限时，请按自己的节奏确认”。
- 声明说明作为弹层的可访问描述始终存在，即使紧凑布局不视觉展示完整段落。
- 手牌同步完成、推荐方案初始化后，初始焦点放到“开始游戏”按钮，方便直接接受建议；尚在同步时先聚焦弹层本身。
- Tab 和 Shift+Tab 始终在声明弹层的可用控件之间循环。提交后控件锁定，焦点回到弹层状态区域，等待其他玩家。
- 不增加 Escape 关闭；声明是必须完成的服务端决策，关闭弹层会制造无法继续但看不出原因的状态。

## 验收

- 568×320 截图首屏能看到完整主按钮和“上滑可调整 · 练习不限时”。
- 无鱼无暗坎与存在推荐内容两种状态的按钮文案准确。
- 完整手牌到齐时主按钮获得焦点；Tab 从最后一个可用控件回到第一个，Shift+Tab 反向循环。
- 手牌同步未完成时确认按钮禁用且焦点位于弹层；同步完成后才移到可操作主按钮。
- 点击确认只提交一次，提交中和已提交状态继续锁定；鼠标和触摸流程不变。
- 375×667 自动旋转、667×375、568×320 和 1280×720 均无溢出或遮挡回归。
