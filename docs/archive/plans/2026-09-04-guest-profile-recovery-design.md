# 本机临时档案自动恢复设计

## 问题

当前 Redis 档案存储只要有一次操作失败，就会在整个服务进程生命周期内永久切换到进程内存。Redis 随后恢复也不会重新尝试，故障期间完成的牌局也不会补写。玩家看到牌局仍可继续，却可能在下次部署或重启后发现局数、胡牌数和累计分丢失，这与“本机临时档案由服务端权威累计”的承诺冲突。

## 方案比较

1. 维持永久内存降级，只增加日志。实现最少，但玩家数据仍会悄悄丢失。
2. 每次请求重新尝试 Redis，不保存故障期间的修改。Redis 能回切，但故障期间的结算仍会丢失，而且持续故障会造成请求风暴。
3. 维护内存镜像和幂等补写队列，按冷却时间探测 Redis；恢复后先补写再读取权威结果。实现略多，但既不阻塞牌局，也能保存短暂故障期间的进度，采用此方案。

## 数据流

- Redis 正常时，读、改名和结算记录都先写权威存储；返回的完整档案同步覆盖进程内镜像。
- Redis 操作失败时，当前操作立即在镜像中完成。改名和结算记录进入内存补写队列，接口继续返回可用结果，牌局不受影响。
- 降级期间使用固定的短冷却窗口，避免每个档案请求都撞击故障中的 Redis。
- 冷却结束后的下一次档案操作先重连 Redis，再按顺序补写队列。结算使用既有 `eventId` 去重；同一档案的多次改名只保留最后一次。
- 补写完成后重新执行当前操作，以 Redis 返回值覆盖镜像。这样即使一次写入已经在 Redis 成功、但响应在网络中断时丢失，重放也不会重复累计。
- 多个同时到达的档案操作在恢复层内串行执行，避免补写队列和镜像发生竞态。

## 边界与错误处理

- 补写队列只存在于服务进程内，目标是覆盖 Redis 的短暂中断；宿主机和 Redis 同时永久损坏不属于临时档案承诺。
- 没有配置 Redis 时仍明确使用纯内存存储，不制造无意义的恢复循环。
- 初次启动连接失败时服务仍可启动；后续档案请求会按冷却窗口自动重试。
- 日志只说明档案服务降级和恢复，不包含档案 token、昵称、房间号或牌局明细。
- 客户端 API、鉴权方式和响应结构均不改变。

## 验收

- Redis 短暂失败后，接口仍可改名、读取和记录结算。
- 同一结算事件在故障期间重复到达只累计一次。
- 冷却窗口内不反复探测 Redis。
- Redis 恢复后，故障期间的最后昵称和所有唯一结算事件都补写成功，统计与镜像一致。
- 初次连接失败不是永久降级；服务无需重启即可恢复权威存储。
