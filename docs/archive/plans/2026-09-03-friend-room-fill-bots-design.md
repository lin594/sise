# 好友房一键补齐电脑设计

> 已由 `83eb03c` 实现并完成回归，本文件仅供历史追溯。

## 背景与证据

568×320 线上等待房已经能固定显示房间操作、邀请链接和开局按钮，但房主创建空房后仍要在可滚动的四个座位卡中逐一找到并点击三次“添加机器人”。首屏底部只说明“还差 3 个座位”，没有给出最省力的解决办法。对不熟悉滚动和房间配置的老年玩家，这会形成“明明看见开局按钮，却不知道怎样让它可用”的阻塞。

本次不改变好友邀请、自由换座、逐席设置难度或房主确认开局的能力，只缩短“朋友人数不足，先让电脑补位”的常见路径。

## 方案比较

### 方案 A：把四个座位卡全面改成紧凑列表

能让四席同时可见，但机器人难度、移除、换座等操作仍需要二级界面，改动面大，也容易在一轮改动中引入新的发现成本。

### 方案 B：创建房间后自动用电脑补满

步骤最少，但会让正在等待朋友的房主误以为座位已被占用，也可能诱导其过早开局。自动行为不符合好友房“先邀请真人”的主要意图。

### 方案 C：显式一键补齐电脑（采用）

在固定底部操作区给房主显示“补齐 N 位电脑”。点击后由服务端一次填满所有空座，采用标准难度和互不重复的随机友好昵称；已有真人、机器人和座位均不改变。四席齐备后按钮消失，开局按钮启用，并明确提示“可以开始对局”。服务端不自动开局，仍保留最后一次有意识的确认。

该方案只增加一个容易理解的捷径，原有逐席添加和调节能力继续存在，适合渐进增强。

## 交互与信息层级

- 好友房房主且存在空座时，底部固定显示次要按钮“补齐 N 位电脑”，与主按钮“开始好友对局”并列；在 568×320 有效画布内无需滚动即可到达。
- 等待房标题直接说明当前状态：房主缺人时显示“还差 N 位即可开局”，四席齐备后显示“四席已就绪”；未入座访客显示“请先选择座位”，已入座非房主显示“等待房主开始”。
- 房主缺人时说明文字使用“邀请朋友，或补齐电脑后开始”；即使极小屏隐藏长说明，底部按钮本身仍能表达下一步。
- 就绪提示使用 `aria-live="polite"`，但不强行移动键盘焦点。点击补位后，焦点停留在消失的按钮可能丢失，因此客户端在状态确认四席齐备后把焦点移到“开始好友对局”。
- 补位按钮和开始按钮在老旧横屏至少 46px 高、15px 字号；正常手机与桌面保持至少 48px。
- 非房主、未入座访客和非好友房不显示补位入口。

## 服务端行为

新增 `fill_bots` 客户端消息，不改变公开状态 Schema：

1. 仅等待阶段、好友房、已入座房主可调用；其他请求返回清楚的 `lobby_error`。
2. 在一次同步处理内枚举空座，逐个创建 `isBot=true`、`isConfiguredBot=true`、标准强度 50 的机器人。
3. 每次取名都以当前房间全部已占用昵称为排除集合，因此机器人之间及与真人都不重名。
4. 已占用座位完全不变；没有空座时返回明确提示，不修改状态。
5. 所有机器人建好后只广播一次权威大厅状态，避免客户端短暂看到半填充布局。

Colyseus 房间消息处理是单线程同步执行；因此同一消息内完成验证和批量写入即可形成房间级原子操作。服务端仍会在真正开始前再次检查四席和真人在线状态。

## 验收

- 服务端单元测试覆盖房主补三个空位、保留已有真人/机器人、随机昵称唯一、标准难度、非房主拒绝、非好友房拒绝和满桌无修改。
- Playwright 在 568×320 验证补位按钮首屏可见、文字包含准确缺额、两枚底部按钮均可稳定触控；点击后出现三位带“机器人”标识的不同友好昵称，按钮消失，标题和就绪提示更新，开局按钮启用并获得焦点。
- 320×568 自动旋转继续使用同一有效画布；1280×720 不破坏原有四席卡片和逐席难度设置。
- 完整服务端测试、客户端/服务端构建和 Playwright 全套通过后再部署到 iMac，并在公网重复 568×320 流程。
