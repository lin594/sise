# 活动牌局跨服务重建恢复设计

> 状态：已实现并完成 iMac 活动牌局重启验收，仅作历史决策记录。

## 问题

当前访客档案已经写入 Redis，但房间、手牌、牌堆和响应流程仍只在 Node.js 进程内。`docker compose up --build -d`、宿主机重启或进程崩溃都会让正在玩的玩家回到大厅；这对需要更长操作时间、也更容易误刷新页面的老年玩家尤其不友好。

## 方案比较

1. 启用 Colyseus `devMode`。它能恢复公开 Schema 和原 roomId，但官方明确不建议用于生产，而且不知道本项目的私有手牌、牌堆和动作队列，不能采用。
2. 部署前等待所有房间结束。实现简单，却不能覆盖崩溃，也会让部署时间不可控，只能作为运维补充。
3. 将完整权威牌局保存为版本化 Redis 快照，进程启动时在监听端口前恢复原 roomId。实现范围较大，但能同时覆盖计划重建和意外退出，采用此方案。

## 状态边界

快照包含公开 `GameState`、牌堆、四家私有手牌、玩家顺序、房间/档案 token 到座位的私有映射、明示公共牌池、庄家过程、待响应牌、集体响应选择、声明暂存、下一局庄家方案、计分结果与决定窗口标识。

不保存旧 WebSocket session、旧定时器句柄、未入座访客、调试/日志统计。原始凭证只存在 Redis 内部快照，不进入 Schema、HTTP 响应、房间元数据或日志。

## 生命周期

- 房间每次广播权威动作后提交一次短防抖快照；同步状态变更不会卡住游戏循环。
- 正常解散或空房回收删除快照；服务整体关停先冻结删除、强制写入全部房间，再让 Colyseus 断开连接。
- 启动时等待 MatchMaker 初始化，读取并校验快照，在 HTTP/WebSocket 监听前用原 roomId 重建。
- 恢复后的配置机器人继续运行；真人标记为离线，保留 token 和座位，先获得正常重连宽限，之后才由机器人临时托管。
- 旧绝对时间和旧 timer 不复用。等待阶段重建座位保留/匹配计时；声明和出牌阶段建立新的本地决定窗口，避免一启动就因过期时间自动操作。
- Redis 暂时不可用时牌局继续，写入失败只输出不含凭证的节流告警；后续状态广播继续尝试。没有配置 Redis 的本地开发保持纯内存语义。

## 一致性与过期

快照以单个 JSON 值原子覆盖，带格式版本、roomId、保存时间和有效期；索引只保存 roomId。启动时丢弃无法解析、版本不兼容、已过期或状态不完整的记录。活动房间采用足够覆盖一晚断线的 TTL，已结束房间采用较短 TTL；恢复后正常写入会续期。

同一 Node.js 事件循环内的牌局变更是同步完成的，防抖序列化只在一个动作完成后取快照，因此不会保存“扣了一半牌”的中间态。恢复时先完整验证快照，再一次性替换房间字段；失败则不注册半恢复房间。

## 验收

- 对局中的公开牌、四家私有手牌、牌堆数量、待响应牌和响应者往返后完全一致。
- 原玩家 token 能回到同一 roomId、同一座位和同一手牌；陌生 token 不能加入已开始房间。
- 服务重启后先显示清楚的断线重连状态，恢复连接后继续当前决定；真人未返回才进入临时托管。
- 正常解散不留下可复活的快照；计划关停则保留。
- Redis 故障不阻断牌局，日志不包含 token 或手牌。
