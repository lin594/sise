# 单人练习房隔离设计

## 背景

新版模式大厅通过 `POST /rooms` 为每次单人练习创建独立房间，但兼容入口 `GET /room-id` 仍会复用任意处于等待阶段的练习房。两个旧页面并发获取入口，或第二名访客持有同一个练习房 ID 时，可能在首局自动开始前进入同一房间。用户选择的是“单人练习”，却会看到陌生真人和非预期座位；这既违背产品语义，也会让昵称、托管和操作提示难以理解。

## 方案比较

- 只复用当前没有连接的等待房：检查与 WebSocket 加入并非同一原子操作，两个请求仍可能同时拿到同一个房间。
- 为等待房增加一次性预约 token：能够复用房间，但需要新的凭证、过期时间和兼容协议，复杂度高于实际收益。
- 每次入口请求创建新练习房，并由房间拒绝第二位新真人：没有共享匹配状态，且房间层能够兜住旧链接或旧客户端。

采用第三种。尚未完成 WebSocket 加入的房间继续由现有等待房空闲计时器回收，因此独立创建不会留下永久空房。

## 行为与边界

- `POST /rooms { mode: "practice" }` 保持现状，每次返回独立房间。
- 兼容接口 `GET /room-id` 改为每次创建新的练习房，不再查询或缓存等待房。
- `POST /reset-room` 仍创建新练习房，但不再更新任何全局“单例房间”状态。
- 所有创建入口共用房间创建限流，避免只读接口改为创建语义后被用于大量制造房间。
- 练习房在 `waiting` 阶段只接受第一位新真人。房中已有真人座位时，第二个没有匹配 token 的访客收到明确错误并关闭连接。
- 持有原房间 token 的玩家在加入保护之前完成座位回收，因此刷新、断线重连和新窗口接管原座均不受影响。
- 好友房仍允许多名真人选座；机器人自动补位和临时托管逻辑不变。

## 验收

- 连续或并发请求两次 `GET /room-id`，获得不同的有效 roomId。
- 两个页面从单人练习入口进入后，各自牌桌只有本人和三名带身份标识的机器人。
- 将第二个新 token 直接加入已有真人的练习房会收到专用终止码；原 token 仍可恢复同一座位。
- 未加入的新练习房在 `WAITING_ROOM_IDLE_MS` 后自动回收。
- 好友房两名以上真人加入、单人练习自动开局、刷新和断线恢复回归均通过。
