# 老旧小屏结算可读性设计

## 背景与证据

当前结算已经能在 667×375 上单列显示，但 568×320 的真实胡牌页面仍把标题、结果摘要、全部玩家长明细和房主操作放在同一个滚动容器中。实测首屏只能看到“你胡牌了 / 本局 +21 分”和房主按钮，看不到任何玩家得分行；滚到明细后，吸底按钮又会覆盖约一行内容。面板滚动高度接近 2000px，老年玩家很难判断还有多少内容、四家的总分在哪里，以及滑动是否会误触整桌操作。

同一局切换到 320×568 后，自动旋转坐标正确：控制栏和结算层没有越出物理视口。因此本轮只调整结算内部的信息层级与滚动模型，不修改整页旋转机制、服务端结算数据或计分规则。

## 方案比较

### 方案 A：继续缩小现有长页

可以让更多内容挤入首屏，但会直接牺牲牌字和分数字号，违背老年用户优先原则，也无法解决房主按钮覆盖内容的问题。

### 方案 B：拆成“总览 / 明细”两个标签页

空间利用最充分，但用户必须先理解标签页，再在两个页面之间来回核对结果；对一次性结算属于不必要的导航层级。

### 方案 C：固定结果与下一步，玩家行按需展开

采用此方案。结算标题和本人输赢固定在顶部，房主操作固定在底部，中间只有一个独立滚动区。四位玩家先以姓名、身份、总分和牌数摘要展示，点击某一行才展开牌组、手牌和分数明细。这样首屏优先回答“谁赢、我多少分、下一步是什么”，又保留完整可核对数据。

## 交互与布局

- 结算面板使用四段结构：标题、本人结果摘要、可滚动明细、底部操作。外层面板本身不再承担内容滚动，底部按钮也不再通过 `position: sticky` 覆盖明细。
- 每名玩家使用原生 `details/summary`。摘要行始终显示姓名、机器人身份、本人/赢家标识、手牌/牌组/流水数量和最终总分；右侧明确显示“查看明细”，展开后改为“收起明细”。原生控件保留键盘展开、读屏状态和较大的整行点击范围。
- 紧凑触屏默认折叠四家明细。本人仍排第一，并且顶部摘要已经单独显示本人输赢，因此不需要默认展开造成首屏拥挤。较大桌面默认展开，保持现有一次看到完整牌局的效率。
- 568×320 下压缩的是留白和重复提示，不缩小结算牌面或操作按钮。标题和结果可并排时使用紧凑布局；“向下滑动查看每家明细”改为更准确的“点击玩家查看牌和得分明细”。
- 中间滚动区必须为唯一纵向滚动区域，具有可聚焦语义和说明。房主按钮始终完整可见；非房主提示同样位于固定底部，不遮挡明细。
- 320×568 自动旋转继续沿用有效画布，结算内容、滚动方向和按钮方向随牌桌一起旋转。

## 状态与错误处理

- `round_result` 未到齐时继续显示现有“正在整理本局得分”，房主操作保持禁用；不渲染空的玩家折叠行。
- 结算数据到齐后才出现玩家摘要。窗口从桌面变为紧凑尺寸时，浏览器可关闭默认展开状态；用户之后的手动展开在本次结算内保持，不写入偏好。
- 下一局、全桌返回和个人退出协议不变。打开整桌返回确认层时继续保持焦点陷阱，新回合状态不得把焦点抢回背景。

## 验收与测试

- 将现有结算端到端测试改为使用仅本地测试桥可用的权威胡牌场景，先完成声明再注入场景，避免依赖随机牌局在 420 秒内自然结束；服务端生产环境仍禁止调试场景。
- 同一局依次检查 667×375、568×320 和 320×568，不新增第二条长牌局。
- 568×320 首屏必须同时看到本人结果摘要、至少前三名玩家的完整摘要行和全部房主按钮；按钮不得与滚动区或玩家行相交。
- 四名玩家默认折叠，展开本人后可见牌组、手牌与分数明细；牌宽不小于 32px、牌字不小于 16px、摘要/明细文字不小于 12px。
- 中间明细区可滚动而结算外层不滚动；最后一名玩家能滚到完整可见。320×568 下结算面板、滚动区和操作区均落在有效画布内。
- 保存 568×320 的折叠总览、本人展开，以及 320×568 自动旋转三张截图并人工检查。

## 非目标

- 不改变任何胡牌、互付或总分计算。
- 不增加新的服务端消息或持久化字段。
- 不为了首屏塞下全部牌而降低现有牌面、文字或触控尺寸下限。
