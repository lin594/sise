# iMac 私网同源入口设计

## 问题

试玩地址目前只能通过 `http://imac.tajuren.cn:3000` 打开，浏览器再直连宿主机 `:2567` 的 HTTP/WebSocket。玩家需要记两个非标准端口，后端也直接暴露在宿主机上。标准 80/443 端口没有服务；仓库的 Traefik 配置依赖当前机器不存在的外部网络、路由变量和 DNS-01 凭证。

域名的公共 DNS 记录为私网 `10.112.145.208`，不能使用要求公网回源的 HTTP-01 自动证书。当前机器也没有可复用的可信证书或 DNS 服务商密钥。此时启用自签证书会让老年玩家看到难以理解的安全警告，不能采用。

## 方案

- 新增 iMac 专用 Compose 覆盖文件，把 Web 同时映射到 80 和原有 3000 端口；无端口地址成为推荐入口，旧书签继续可用。
- Web Nginx 代理 `/matchmake`、健康检查、房间、私有状态和临时档案 API，并正确转发 WebSocket Upgrade。
- iMac 前端构建使用同源 `ws://imac.tajuren.cn` 与 `http://imac.tajuren.cn`，不再让浏览器直连 2567。
- iMac 覆盖文件移除服务端宿主端口，只允许 Web 容器通过 Compose 内网访问；服务端信任唯一一层 Nginx 代理并只允许无端口与过渡端口两个前端来源。
- 普通本地 Compose、开发端口和独立 Traefik 配置保持不变。

## TLS 边界

同源 HTTP 减少了端口暴露和跨源复杂度，但不等于浏览器 TLS。域名位于私网时，可信 HTTPS 需要 DNS-01 自动签发或受管客户端证书信任。拿到 DNSPod API 凭证或既有证书设施后再启用 443；在此之前文档必须明确它是受控私网试玩入口，不能标为公网正式环境。

## 验收

- `http://imac.tajuren.cn/` 返回页面，`:3000` 仍可访问。
- `http://imac.tajuren.cn/health` 返回服务健康；浏览器可通过同一主机的 `/matchmake` 建房、进入声明并自动恢复。
- iMac 宿主机不再监听 2567；Redis 仍只在 Compose 内网。
- CORS 接受两个实际试玩来源，拒绝其他浏览器来源；`X-Forwarded-For` 只在单层可信代理下生效。
- 667×375 浏览器 smoke 能使用无端口地址完成进入、声明和退出。
