# 开局请求可见回执设计

## 问题

房间已经建立后，房主点击“开始好友对局”或“电脑补位，立即开始”，以及单人练习自动发起开局时，客户端只发送 `start_game`。在服务端阶段切换到声明前，按钮仍可能保持可用且没有进度说明。网络较慢或玩家连续点击时会重复发送请求，也会让不熟悉网络状态的玩家误以为按钮没有生效。

## 方案

- `useRoom.startGame()` 返回消息是否实际交给当前 WebSocket；连接不可用时不伪装成提交成功。
- `App` 统一持有房间内开局提交状态。第一次成功发送后立即锁住开始按钮，好友房显示“正在开始好友对局…”，快速配桌显示“正在补齐并开局…”，练习房显示“正在开始练习…”。
- 按钮下方显示“开局请求已发送，请稍候”，不增加遮罩，仍允许玩家查看座位和连接情况。
- 收到非 `waiting` 权威阶段后清除提交状态；服务端返回大厅错误时立即恢复按钮并保留错误原因。
- 8 秒仍未收到阶段变化时恢复按钮，并提示“暂未确认开局，请再点一次”，让玩家能主动重试而不会永久卡死。
- 同一提交窗口内的连续点击只发送一次 `start_game`。房间准备条件变化、离房或连接失效时也清理旧提交状态。

## 边界

- 不新增服务端协议；现有阶段快照和 `lobby_error` 是权威回执。
- 不改变好友房准备规则、快速配桌倒计时或机器人补位逻辑。
- 前置建房的 `enteringLobby` 与房间内开局的提交状态保持分离，避免一个状态误锁另一个阶段。

## 验收

- 暂停发送 `start_game` 时，按钮立即禁用、显示对应玩法文案，提示区域说明请求已发送。
- 同一帧连续触发只产生一条消息；恢复发送后正常进入声明。
- 发送失败或超时后重新开放按钮，不清空昵称、房号、座位或准备状态。
- 568×320 下等待文案不换出按钮边界，固定底部操作区不遮挡座位。
