# 浏览器存储受限韧性设计

## 问题

客户端已经为本机昵称、显示设置、临时档案和房间重连保存少量数据，但各处直接访问 `localStorage` 或 `sessionStorage`。部分隐私模式、内嵌浏览器、家长控制或存储配额异常会让这些 API 在读取属性或调用方法时抛出 `SecurityError`。当前首页初始化、确认昵称、修改设置和入房都可能因此中断；玩家看到的只是白屏或按钮没反应。

这类环境无法承诺刷新后的自动恢复，但仍应允许玩家在当前页面完成一局，并在进入前用普通中文说明限制。临时档案、房间 token 和内部异常不能出现在地址或提示中。

## 方案比较

1. 在每个调用点单独加 `try/catch`：改动小，但重复逻辑多，未来很容易再次漏掉。
2. 统一安全存储工具并提供页面内存兜底：所有业务只调用同一接口；可在本页继续使用昵称、偏好和连接凭证，同时准确判断能否跨刷新保留。采用此方案。
3. 检测失败后禁止开局：实现最简单，但把可降级问题变成无法游戏，不符合老年玩家优先原则。

## 行为设计

- 新增统一安全存储层，依次尝试本地存储、会话存储和页面内存；单个存储失败不能阻止其他层。
- 写入始终同步到页面内存，并尽力写入两个浏览器存储；删除同样清理三层，防止退出后旧房间凭证在本页复活。
- “能否长期保存”只以可读写的 `localStorage` 为准。仅有会话存储时仍可支撑当前标签页刷新，但不能宣称设备会长期记住。
- 昵称、昵称历史、牌面/提醒偏好、临时档案 token、房间号和房间 token 全部迁移到统一工具。
- 本地存储不可用时，昵称页不显示“这台设备会记住昵称”，改为“本次仍可正常游戏；关闭页面后可能需要重新输入昵称，牌局中请尽量不要刷新”。好友邀请入口使用同样明确但不恐吓的文字。
- 存储受限时隐藏“本机临时档案”摘要，避免把只能存在当前页面的随机身份误写成可找回档案；服务端档案请求仍可非阻塞工作，不影响当前牌局。
- 正常浏览器的文案、数据格式、键名、房间协议和服务端 Schema 完全不变。

## 错误与隐私边界

存储异常不上传、不展示浏览器内部异常，也不写入公开牌桌。安全层只返回空值或布尔能力；上层继续使用现有默认值。密码、正式账号和跨设备同步不属于本轮范围。

## 验收

- 在页面脚本执行前让 Storage 的读、写、删全部抛错，首页仍正常显示并自动生成可编辑昵称。
- 568×320 上限制说明、输入框和两个按钮完整可达，正文不小于 14px。
- 确认昵称后可进入三模式大厅；本机档案摘要不出现。
- 选择单人练习后能连接、自动开局并进入声明阶段，全程没有 `pageerror`。
- 正常存储环境的首次入口、档案、偏好与断线重连回归继续通过。
