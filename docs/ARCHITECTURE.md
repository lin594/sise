# 系统架构

## 1. 总览

- 前端：Vue 3 + TypeScript，使用 `@colyseus/sdk` 0.18 连接实时服务。
- 服务端：Colyseus Core 0.18 + Schema 5 + TypeScript，使用 Express 提供少量 HTTP 辅助接口。
- 实时通信：Colyseus 房间状态补丁与自定义 WebSocket 消息。
- 运行模式：单人练习、公开快速配桌和好友同桌私有房。
- 数据保存：权威牌局在进程内运行，并以版本化私有快照写入 Redis，单服务重建后可恢复原房间；免注册访客的聚合档案也写入 Redis。未配置 Redis 的开发环境仍可游戏，但进程退出后不会恢复房间；档案在 Redis 短暂故障时使用内存镜像和变更日志，恢复后自动补写。

规则裁决全部在服务端。客户端只渲染公开状态、本人的私有手牌和服务端签发的合法动作，不能自行决定胡、吃、碰、开或弃牌是否成功。

## 2. 状态边界

### 2.1 公开 `GameState`

主要字段：

- `phase`: `waiting | declaring | playing | ended`
- `stateRevision`：每次权威公开状态发布时严格递增的版本号
- `roomMode`: `practice | match | friends`
- `matchStartsAt`：快速桌自动补位开局的服务端权威截止时间；其他模式为 0
- `hostPlayerId`、`dealerId`、`dealerPickerId`
- `currentPlayerId`、`currentTurnPlayerId`、`previousPlayerId`
- `pollOriginPlayerId`、`activeResponderId`
- `responsePhase`: `collective | local_upper | local_draw`
- `responseEndsAt`、`declareEndsAt`
- `players: MapSchema<PlayerState>`
- `publicDiscardPile`、`responseCard`、`targetCard`、`dealerCard`
- `deckCount`、`lastAction`

`PlayerState` 公开名字、固定座位索引、连接/机器人状态、等待大厅准备状态、主动托管状态、机器人强度、手牌数量、声明状态、弃牌、明示牌组、鱼和本桌累计分。对手只能看到 `handCount`，看不到实际手牌。`lobbyReady` 仅表示好友房非房主真人对下一次从等待大厅开局的确认；`isAutoPlay` 表示在线真人主动托管，始终与配置机器人身份 `isConfiguredBot`、临时断线控制 `isBot` 分离。

`GameState.scoringMode` 保存好友房的 `single` / `cumulative` 计分方式，`completedRounds` 是本桌已经完成的结算次数。服务端只允许好友房房主在等待阶段且首局结算前发送 `set_scoring_mode`。每局 `round_result` 生成后由唯一的终局入口把本局总分原子地并入各座位 `cumulativeScore`，同时写入 `roundNumber`；重复到达终局路径不能重复累计。整桌返回大厅只清理本局运行态，不清理好友房累计分；解散房间才结束这份临时榜单。

`generalArea` 与 `wildcardPool` 是历史兼容字段；`wildcardPool` 不作为万能牌替代参与组牌。当前单张将或金条的收取统一写入一张牌的 `exposedArea` 牌组，不创建新的特殊牌展示区。

### 2.2 私有房间状态

服务端内存保存：

- `playerHands: Map<seatId, Card[]>`
- session、player token 与 seatId 的映射
- 机器人座位集合
- 当前待响应上下文及集体选择
- 当前必须弃牌的座位
- 超时任务、断线托管和本局结算快照

上述权威数据除旧 WebSocket session 和计时器句柄外，会在每次完整动作广播后生成 `ROOM_RECOVERY_VERSION` 版本的 Redis 快照。每个房间的短时间连续广播只写最后一份，写入在房间事件循环之外串行执行，不让 Redis 延迟阻塞出牌。快照包含四家真实手牌、牌堆、待响应上下文和房间/档案 token，因此只能保存在内部 Redis，不能进入公开 Schema、房间元数据、HTTP 响应或日志。活动/等待房快照保留 24 小时，已结算房保留 6 小时，后续写入续期；正常解散和空房回收会删除对应记录。若当时已经无人连接，快照还会保留既有空房清理截止时间，连续重启只能继承剩余时间，不能反复把废桌续期。

服务启动先等待 MatchMaker 初始化，再读取并校验快照，用原 roomId 重建房间，全部完成后才开放 HTTP/WebSocket 监听。旧 session 和声明/响应等牌局截止时间不会复用：配置机器人继续运行，真人先标记离线并获得新的重连宽限，声明/响应计时从安全的完整窗口重新建立；原 `playerToken` 随后仍能回收同一座位和私有手牌。只有用于防止无人房间泄漏的清理截止时间按原值继承。优雅关停在 Colyseus 断开客户端之前强制写入所有房间，并抑制关停过程的正常删除。Redis 故障只让本次快照不可用，不中断当前游戏；后续状态变化会再次尝试，但进程与 Redis 同时永久故障仍无法恢复未落盘状态。

私有手牌通过 `private_hand` 消息和受 token 保护的 `/private-state` 恢复，不进入公开 Schema。客户端使用 `Authorization: Bearer <playerToken>` 请求该接口，响应带 `Cache-Control: no-store`；服务端暂时兼容旧客户端的查询参数 token，但新代码不得再把凭证写入 URL。好友邀请访客尚未选座时只同步公开大厅状态；客户端接收 `lobby_presence` 并保持本地座位为空，不启动私有状态请求。收到 `session_token` 确认入座后立即补拉一次；正常更新依靠 Colyseus Schema 事件和完整 `room_snapshot`，仅在加入恢复、页面重新可见或检测到私有手牌缺失时按需发送 `sync_state`，不再每 250ms 归一化整张牌桌或周期拉取完整私有状态。

本机访客档案使用独立的 `profileToken`，不能复用房间 `playerToken`。客户端只通过加入参数或 `Authorization: Bearer` 传递它；服务端仅在私有座位映射中临时绑定，不写入 Schema、邀请地址或普通日志。Redis 键使用凭证的 SHA-256 摘要。每个权威 `round_result` 以 `roomId + roundNumber + profile hash` 幂等记一局，只累计真人的已玩局数、胡牌数和本局总分；配置机器人忽略，真人临时托管仍归原档案。

`RecoveringGuestProfileStore` 串行协调 Redis 和进程内镜像。Redis 正常时，每次权威结果覆盖镜像；操作失败后，接口立即从镜像完成并把最后一次改名、唯一结算事件放入内存补写队列。短冷却窗口内不重复探测，之后的下一次档案操作会显式重连、按顺序重放并以 Redis 返回值校准镜像。结算事件继续依赖 Redis 的事件键去重，因此“写入已成功但响应丢失”也不会重复累计。降级和恢复日志不包含凭证或玩家资料。该机制覆盖短暂存储中断，不把进程内队列伪装成正式账号级持久化；服务进程与 Redis 同时永久丢失仍无法找回。

决策倒计同样由服务端权威管理。`available_actions`、本人房间快照和 `/private-state` 会携带 `decisionTimer`，包含是否不限时、加时权限、加时量、当前总时长、准确截止时间和一次性决策指纹。单人练习只对当前在线真人关闭声明与操作超时；机器人及断线托管继续计时。新客户端发送 `action`、`discard_card` 和 `request_more_time` 时都回传该指纹；服务端忽略不属于当前窗口的迟到请求并重发当前可用动作，避免重复点击或慢网络消息作用于下一个玩家、下一次操作或下一局。未携带指纹的旧客户端仍按原协议兼容。公开 Schema 补丁不含该私有字段，客户端收到不带它的公开补丁时必须保留最近一次私有结果。

公开 Schema 补丁与同次完整 `room_snapshot` 使用相同 `stateRevision`。服务端在每次发布前只递增一次，恢复缺少该字段的旧快照时从 0 升级。客户端拒绝低于当前版本的输入；相同版本只合并私有手牌、动作和计时，不替换公开牌桌对象；更高版本若可见指纹未变化，也只推进版本游标。玩家在归一化和生成指纹前统一按 `seatIndex` 排序，指纹覆盖所有实际渲染的身份、牌区和阶段字段。这样 Schema 与完整快照无论以何种顺序到达，都不会让旧公共状态覆盖新状态或改变座位顺序。

集体待响仍使用服务端权威队列，但允许尚未轮到、尚未响应的真人预先提交选择。预选只写入当前 `pending.collectives`，不移动游标、不清除当前响应者计时器；轮询随后跳过已预选座位，最终仍由同一 `pickCollectiveWinner` 按“胡优先，再按座次开/碰”决定结果。上家牌的预吃和抓保留客户端延迟选择；摸牌者的吃由服务端直接登记到 collectives，胡/开/碰优先裁决后再执行。普通自摸无人取得时直接转下家的 local_upper，不重新建立 collective。

客户端不能只凭公开回合状态开放操作。进入声明或对局后，必须以本人公开 `handCount` 与私有手牌长度相等作为私有状态就绪条件；数量不一致时冻结选牌和动作，并按需请求 `sync_state` 与私有状态补拉。开局发牌展示动画尚未结束时也保持冻结。服务端先建立新局阶段、定庄信息和公共手牌数，再发送带私有手牌的完整快照；客户端使用 `roomId + roundNumber` 作为发牌展示键，只有首次看到该局完整手牌时启动一次。动画以绝对时间计算进度，掉帧时跳过已错过的牌；进入声明即强制显示完整手牌。组件重挂载、声明变化、普通同步和迟到快照均不能再启动发牌。

新牌局动画使用服务端公开 tableTransitions 有序事件和 presentationUntil 截止时间；Schema 用 tableTransitionsJson 保存同一数据，恢复快照一并持久化。事件仅包含已公开移动牌、起终位置、局号、序号和时间，最多保留本局最近 32 条。客户端按绝对时间、约 30 帧/秒绘制，过期和重复消息不重播；普通飞牌在服务端展示窗口结束前提前抵达并保持精确终点。只有目标牌面的真实 DOM 矩形可作为落点，目标尚未挂载时跳过动画并直接呈现权威状态，不能使用牌区或座位中心猜测。展示间隔内服务端拒绝操作并延后机器人与响应计时，终局通过私有 pendingPresentationEnd 恢复延迟结算。无客户端的模拟牌局跳过展示延迟。旧协议仅保留开局牌背动画和动作语义键去重，不再为出牌、组牌或摸牌生成估算轨迹。四条流水在组件生命周期内保持固定 DOM 容器，数据归属来自排序后的座位环；方向偏好只镜像内容位置。当前回合、流水强调和定庄结果使用静态标记，动画仅允许合成层的 `transform` 与 `opacity`，不动画化布局尺寸、`filter` 或 `box-shadow`。

客户端根据服务端 `lastAction` 维护本轮只读的最近操作记录。解析层把座位号与动作码拆分，并从同一权威快照复制可见的定庄牌或待响应牌名称；界面层再用当前公开玩家昵称、本人、配置机器人和临时托管身份生成中文说明。该记录不回写服务器、不参与状态机，下一局开始或离开房间时清空。自动摸牌、未知动作码等过程信息会在客户端过滤，避免把技术流水当成玩家信息或直接泄漏到界面。

生产服务只接受 `CORS_ALLOWED_ORIGINS` 明确列出的浏览器来源。Express 辅助接口、Colyseus 匹配接口和 WebSocket 握手共用同一来源策略；没有浏览器 `Origin` 的健康检查与服务间调用仍可访问。开发环境默认放开来源，便于局域网手机联调。Colyseus 管理监控页在生产环境默认关闭，只能通过显式配置临时启用。

服务启动必须通过 `gameServer.listen()`，由 Colyseus 在同一个 HTTP Server 上挂载 `/matchmake/*` 路由并保留 Express 辅助接口；不能绕过它直接调用原生 `http.Server.listen()`。房间将 `autoDispose` 在类初始化阶段关闭，再由业务层的等待房和活动房空闲计时器负责回收。等待房计时器在 HTTP 创建完成后立即启动，首名玩家加入时清除；这样既给“创建房间 → 浏览器建立 WebSocket”留出宽限，也会回收创建后从未加入的废弃房间。

所有房间创建入口共用按客户端 IP 计算的内存限流，恢复私有状态使用独立限流；超限返回 `429`、`Retry-After` 和稳定错误码，并通过 CORS 暴露限流响应头供客户端显示准确等待时间。直接访问服务时不信任转发头；Traefik 部署只信任紧邻的一层代理，以免伪造 IP 绕过限流。HTTP 响应不公开 Express 技术标识。限流状态不跨进程共享，当前单进程部署足够使用。

新版和兼容入口每次都创建独立练习房，不查询或复用其他等待房。练习房在房间层只接受首位新真人；原 token 的座位回收先于这项检查，因此刷新和断线重连不受影响。好友房仍按邀请链接允许多名真人选座。快速桌通过 Colyseus `joinOrCreate` 查询 `roomMode=match, matchOpen=true`，按已连接人数降序把真人集中到最接近满员的桌；房间开始后只关闭匹配元数据，不锁死原 token 的直接重连。尚未完成 WebSocket 加入的空房由等待房空闲计时器自动回收。

## 3. 座位、身份与房主

- `sessionId` 属于一次连接，断线后会改变。
- `seatId` 是 `seat_0` 至 `seat_3` 的固定逻辑座位，回合和规则始终按 seatId 运转。
- 第一次加入时确定 `playerToken + seatId`；客户端按房间保存 token，重连时用它恢复原座。新 token 使用系统加密随机源生成 192 位随机值；服务端仍接受旧格式，避免升级后把已有玩家踢出原座。
- `profileToken` 是当前浏览器的免注册档案凭证，跨房间但不代表正式账号；它只关联昵称与聚合战绩，清除浏览器数据后不可恢复。
- 客户端所有业务存储都经过 `safeStorage`：读取依次尝试 `localStorage`、`sessionStorage` 和模块内存，写入与删除覆盖所有可用层；任一属性读取或方法调用抛错都被隔离。只有 `localStorage` 真实可读写时，界面才宣称设备会长期记住昵称并显示本机档案。Colyseus 客户端初始化也在同一保护边界内，避免第三方 SDK 读取被禁用的 Web Storage 时中断入房。
- 同一 `playerToken + seatId` 同时只允许一个活动会话。新窗口或新设备恢复座位时，服务端先向旧连接发送 `session_replaced`，再用 4102 关闭码结束旧连接；旧客户端必须停止重连，不能与新会话反复抢座。
- 昵称在首次入座时完成 Unicode 归一化、去除不可见控制字符并成为该座位的稳定显示名；同房真人同名会自动追加“（2）”等后缀。预先配置的机器人创建时从友好昵称池随机选择一个未被本桌占用的名称，此后该座位名称保持稳定；重连请求不能借机改名。
- 昵称页进入未连接的玩法大厅时只更新本机 `sise_entry_name` 与历史列表，不创建房间或签发 token。玩家可以从玩法大厅返回修改昵称；只有选择单人练习、好友同桌或打开邀请链接后才发起房间连接，因此返回修改不需要执行离房流程。
- 好友房 `claim_seat` 允许已入座真人移动到另一个空座，服务端收到的消息顺序就是最终座位顺序。客户端因此在 `mySeatId` 权威变化前只允许一条选座消息，并记录目标座位供界面显示；大厅错误、断线、换房或 8 秒无变化后解除，避免慢网连点把玩家移动到非预期座位。
- 等待大厅断线座位会短暂保留；进行中断线先进入默认 5 秒重连宽限，期间仍视为离线真人且机器人不得代操作。宽限到期后才由机器人托管，同 token 重连后可夺回控制。框架的 4000 主动离开关闭码与网络异常关闭分开处理：前者立即释放等待座位或启用托管，后者保留恢复机会。
- 临时托管不修改真人昵称。`isConfiguredBot` 标记预先配置或自动补位的机器人，是机器人身份的权威依据，不得通过昵称格式推断；`isBot && !isConfiguredBot` 表示真人座位暂由机器人控制，客户端据此显示不同身份状态。`round_result` 同步携带 `isConfiguredBot`，用于结算身份标识和付款人文案。
- 房主权限与座位号分离。房主意外断线时在对应恢复宽限内暂不转交；及时重连仍是原房主。宽限到期进入托管或等待座位到期释放后，才转给座位顺序最靠前的在线真人；主动退出则立即转交。
- 单人练习开局自动补足机器人；快速桌在权威倒计时截止或首位玩家明确要求时用标准机器人补位；好友房只使用房主显式配置的机器人。
- `botStrength` 在服务端继续使用 0–100 数值参与策略权重，保证旧客户端兼容；当前好友房界面只发送 20、50、85 三个预设，并分别显示为“轻松、标准、高手”，避免触屏精细滑动。

客户端牌桌先按服务端 `seatIndex` 的 A→B→C→D 权威顺序排列，再以本人座位为起点旋转；不能使用玩家加入或换座造成的集合插入顺序。座位方向偏好只改变左右布局，不改变上述映射或服务端行动顺序。

### 3.1 客户端连接恢复

- 从玩法大厅发起建房或配桌时，`App` 以独立的启动模式状态区分练习、好友和快速配桌：HTTP 建房阶段锁定原页面，进入 WebSocket 后仍显示对应玩法语义，不能复用“恢复牌局”文案。取消会递增连接代次、清理尚未完成的房间凭证并回到保留原选择的玩法页；任何迟到的加入结果必须自行离开且不得写回界面。
- 断线时保留最后一份公开牌桌、本人手牌和动作上下文，不把玩家送回空白加载页。
- 保留的牌桌只供查看；连接恢复前吃、碰、开、胡、过和出牌全部禁用，避免向失效连接提交动作。
- 浏览器重新联网或页面重新变为可见时立即重试；网络抖动、服务短暂不可用等可恢复故障按指数退避持续重试，间隔上限为 15 秒，不因固定次数用尽而放弃。
- 房间不存在或已回收、座位失效、房间已满、玩家被移出，以及同一座位已在其他窗口恢复，均属于终止性状态。客户端进入 `closed`、清除重试计时器并显示原因；不能把这些状态误当网络抖动无限重试。
- 浏览器刷新或页面被系统回收后，若本机仍保存 `roomId + playerToken + 昵称`，客户端直接恢复原房间和座位，不重新经过昵称入口。
- 房间或恢复流程激活时，`App` 在当前浏览器历史之上维护一个不含凭据的保护状态。`popstate` 先恢复该状态并关闭最上层模态内容或请求现有离房确认；退出、终止性恢复失败和远端解散统一移除保护并清理房间查询参数。`useRoom` 更新邀请地址时保留现有 `history.state`，不能意外抹掉保护标记。
- 恢复成功后重新获取权威公开快照、私有手牌和动作，再短暂显示“牌局已恢复”，并说明托管期间的最新牌局已同步。
- `/private-state` 是消息丢失时的安全兜底，常规轮询间隔为 5 秒；连接正常但公开手牌数与私有手牌数量不一致时改为每秒补拉私有状态，不主动离房重进。
- 每次私有状态请求绑定发起时的连接代次、roomId、playerToken、私有 WebSocket 消息版本和 HTTP 请求顺序。退出、换房、重连或后续出牌消息之后才到达的旧响应必须丢弃，不能把旧座位、旧手牌或旧动作短暂写回当前页面。
- 声明面板的选择只保存在当前客户端，断网时不清空；连接未就绪时禁止发送。提交后由公开 `declaredReady` 状态确认成功，客户端以 3.5 秒恢复窗口兜底：若权威状态没有到达则解除本地提交锁并允许重试，服务端对已经声明的座位保持幂等忽略。
- 自动恢复页始终提供放弃入口；放弃后终止当前连接尝试、清除该房间凭证并返回首页。连接尝试以递增序号隔离，迟到的旧结果不能覆盖新连接或取消状态。
- Colyseus `Room` 是带监听器和连接身份的 SDK 实例，客户端必须使用 `shallowRef` 保存，不能让 Vue 深层代理破坏 `room.value === joined` 的当前连接判定。公开牌局快照仍可使用普通响应式状态。
- SDK 自带自动重连关闭：服务端没有使用 `allowReconnection()`，稳定身份恢复统一由应用层 `playerToken` 完成。一次网络恢复只建立一个替代连接，避免 SDK session 重试与座位 token 重试并发抢占。

## 4. 房间生命周期

### `waiting`

昵称入口后进入模式大厅。每次单人练习创建只属于该玩家的独立房间，首位真人入座后不再接受其他新身份。好友房访客可以通过 `roomId` 加入并原子领取空座；房主可以添加、调整或移除机器人，并在四席就绪时开局。

客户端把 `start_game` 是否交给当前 WebSocket 作为本地提交起点，并以服务端离开 `waiting` 的快照作为成功回执。提交窗口内锁定重复发送；`lobby_error`、连接中断、换房会立即解除，8 秒没有权威变化则允许重试。这个短期提交态不改变服务端的开局条件，也不能提前展示声明或手牌。

普通玩家的 `set_lobby_ready` 也使用目标值提交态：客户端不提前改写公开座位，而是等本人 `lobbyReady` 与目标值一致后完成。等待期间相反目标不能并发；大厅错误、断线、换座、换房或 8 秒无权威变化会解除。服务端仍是所有人看到“已准备 / 未准备”的唯一来源。

快速桌自动领取第一个空闲固定座位。首位真人建立 `matchStartsAt`，后续加入不会延后它，四名真人到齐只会把它提前到短暂展示窗口。房间快照将绝对截止时间与同一时刻的 `serverNow` 一起发送，客户端据此校正本机时钟偏差；倒计时不能假设手机与服务器时间完全一致。截止时服务端先验证所有保留真人都在线，再把 `matchOpen` 设为 false、补齐标准机器人并进入开局；有保留真人断线时维持原截止时间但暂停执行。四个逻辑座位已被占满时，即使其中一个连接暂时离线，也必须从公开匹配结果中移除该桌，避免第五人被送入后才遭拒绝。快速桌拒绝选座、计分修改、机器人管理、整桌下一局和整桌返厅消息。

好友房房主还可发送 `fill_bots`。服务端只在等待阶段验证一次房主身份，再在同一消息处理内用标准难度配置机器人填满全部空座，逐个排除当前已占用昵称，最后只广播一次大厅动作状态。该操作不替换已有座位、不自动开局，满桌、非房主或非好友房请求均只返回 `lobby_error`。

好友房非房主真人通过 `set_lobby_ready` 修改自己的 `lobbyReady`。服务端启动首局前同时校验四席、真人在线和所有非房主真人已准备；配置机器人隐式准备。网络中断不清除该值，但离线状态仍阻止开局；换座、首局计分方式变化和 `return_lobby` 清除真人准备。房主以 `start_game` 作为自己的确认，已有 `next_round` 流程不额外增加准备步骤。

好友房等待页的标题、可滚动邀请/座位内容和底部下一步是三个独立布局区域，避免低高度画布的固定操作覆盖座位。等待阶段的个人离房与牌局中退出复用 `leaveRoom()`：先禁止重连并作废当前连接代次，再清理房间级 token、活动房号和 URL 参数，最后以框架主动离开关闭码关闭现有连接；服务端据此立即释放或托管并转交房主，不新增应用消息协议。

等待阶段的好友房房主可发送 `dissolve_room`。服务端再次校验房型、阶段与房主身份，向全部连接广播 `room_dissolved` 后清空座位 token，并用终止关闭码结束房间。客户端把该消息作为不可重连事件，作废当前连接代次、清除凭证与 URL 房号并返回模式大厅；普通个人离房仍沿用原逻辑，不会关闭其他玩家的桌。客户端还单独跟踪尚未完成 WebSocket 加入的目标 roomId：玩家在连接中取消时，连接代次立即失效，房间级临时 token 也按该目标清除，迟到成功的连接只能主动离开，不能重新把页面带回房间。

好友邀请二维码完全由客户端根据当前页面来源、路径和公开 `roomId` 生成，不新增服务端二维码接口，也不把 `playerToken`、`hostKey` 等身份信息编码进去。生成失败时只退回可选择的同一公开邀请链接；普通 HTTP 试玩环境不依赖系统分享或现代剪贴板能力也能让身边牌友扫码加入。

客户端后端地址由统一解析器生成：HTTPS 页面默认使用 HTTPS API 与 WSS，HTTP 页面默认使用 HTTP API 与 WS；显式配置其中一个 `VITE_SERVER_*` 地址时，另一条链路从同一主机、端口和路径推导，并清除查询串、片段及尾部斜杠。正式环境仍建议显式写出两项，Traefik 终止 TLS 后把 HTTPS/WSS 转发到容器内同一个 HTTP 服务。iMac 是 HTTP/WS 测试环境：专用 Compose 覆盖让 Web Nginx 在 80 端口同源代理 HTTP、`/matchmake/*` 与 WebSocket，3000 只保留旧书签兼容，2567 不再映射到宿主机；该路径不参与正式 TLS 配置。Web Nginx 通过 Docker 内置 DNS 动态解析 `server` 服务名，并把上游放在共享内存区；因此只替换服务端容器、其内网地址变化时，不必同时重启 Web 网关，已有页面可在短暂断线后继续用原房间凭证恢复。

房间即使尚无任何连接也已进入业务生命周期：等待宽限内允许首名玩家加入，超时仍为空则主动断开并从房间注册表移除。最后一名玩家离开后复用同一机制重新计时，避免仅通过 HTTP 创建、从未完成 WebSocket 加入的房间永久驻留。

### `declaring`

服务端完成定庄与发牌，客户端播放短动画；随后玩家一次性声明鱼与暗坎。四座均提交或声明超时后进入正式对局，机器人和断线托管座位自动声明。

### `playing`

状态机按 [GAME_RULES.md](GAME_RULES.md) 运行集体响应和本地响应。动作执行遵循“先验证、后统一扣除”：吃、碰、开必须验证目标牌、全部手牌和唯一牌 ID，再一次性更新手牌、牌池与明示牌组，防止半成功状态。

### `ended`

服务端先把状态切到结束阶段，再广播并保存权威 `round_result`。客户端可以立即显示“正在整理本局得分”，但必须等包含四家明细的 `round_result` 到齐后，才允许后续操作，避免状态补丁与结果消息先后到达时跳过结算。结果到齐后，客户端把固定的本人输赢、独立滚动的玩家明细和固定操作分层；紧凑屏默认折叠每家长明细，桌面默认展开，但两者读取同一份权威结果。好友房存在其他真人时，客户端在发送 `next_round` 前增加可取消、约束焦点的全桌影响确认；只有房主可发整桌命令。练习房显示“再练一局”与“返回玩法选择”，前者发送下一局，后者执行个人 `leaveRoom()` 后回到三模式选择；新手牌必须等新局快照到达且离开旧结算状态后才可渲染。`next_round` 与 `return_lobby` 以互斥的本地提交状态等待服务端离开 `ended`，期间只允许一条整桌命令；大厅错误、断线、换房会立即解除，8 秒没有权威变化则恢复重试。快速桌隐藏整桌生命周期控制，每名真人通过客户端先执行个人 `leaveRoom()`，清理旧房凭证后重新 `joinOrCreate`；旧桌不受影响。任何真人仍可以从客户端个人退出，进行中的空座由机器人继续托管。

## 5. 消息接口

客户端发往房间的主要消息：

| 消息 | 用途 |
|---|---|
| `start_game` | 练习/好友房房主开局，或快速桌首位玩家请求立即电脑补位 |
| `declare_setup` | 一次提交鱼与暗坎声明 |
| `declare_kongs` | 旧客户端兼容的暗坎声明 |
| `action` | 提交胡、开、碰、吃或过 |
| `discard_card` | 提交已确认的弃牌 ID |
| `request_more_time` | 携带当前 `decisionKey` 申请一次服务端权威加时 |
| `set_auto_play` | 在线真人开启或取消当前座位的主动托管 |
| `set_scoring_mode` | 好友房房主在首局开始前选择单局或本桌累计计分 |
| `set_lobby_ready` | 好友房等待阶段的非房主真人确认或取消准备 |
| `dissolve_room` | 好友房房主在等待阶段解散整桌 |
| `sync_state` | 请求重新发送快照、私有手牌和动作 |
| `claim_seat` | 好友房领取空座 |
| `fill_bots` | 好友房房主用标准难度机器人一次补齐全部空座 |
| `add_bot` / `update_bot` / `remove_seat` | 房主管理座位 |
| `next_round` / `return_lobby` | 房主结算操作 |
| `debug_setup` | 仅非生产环境显式开启后，由房主构造可重复测试牌局；生产不注册该入口 |

服务端返回的主要自定义消息：

- 身份与快照：`session_token`、`room_snapshot`、`lobby_presence`。
- 私有数据：`private_hand`、`available_actions`。
- 结果：`hu_result`、`round_result`。
- 牌局操作回执：服务端接受 `action` 或 `discard_card` 后返回 `action_received`；拒绝时由 `action_rejected` 携带稳定原因码、当前 `decisionKey` 和玩家可读说明。回执只确认权威状态机已接收请求，不代替后续房间状态。
- 其他失败反馈：`join_error`、`lobby_error`、`declare_rejected`、`removed_from_room`。
- 测试反馈：`debug_applied`；仅在非生产环境设置 `ENABLE_DEBUG_SCENARIOS=1` 后存在，且非房主调用返回失败。

动作协议只有 `pass`，没有单独的 `zhua`：`local_upper` 阶段的 `pass` 在产品语言中显示为“抓”。特殊牌本地阶段不提供 pass，单张吃牌也通过普通 `chi` 的单牌候选提交；`FORCE_TAKE` 仅是服务端兜底标记，前端统一显示为“吃”。

## 6. HTTP 辅助接口

| 方法与路径 | 用途 |
|---|---|
| `GET /health` | 服务健康检查 |
| `POST /rooms` | 创建指定模式的独立房间 |
| `GET /room-id` | 兼容旧客户端：创建一个新的独立单人练习房，响应禁止缓存 |
| `POST /reset-room` | 兼容旧客户端：创建一个新的独立单人练习房 |
| `GET /private-state` | 按 Bearer 房间 token 恢复本人私有状态，响应禁止缓存 |
| `GET /guest-profile` | 按 Bearer 档案凭证读取或创建本机临时档案，响应禁止缓存 |
| `PUT /guest-profile` | 按 Bearer 档案凭证更新规范化昵称，响应禁止缓存 |

项目没有公开房间列表、正式账号鉴权 API 或多服务实例之间的活动房迁移。单服务重建恢复走内部 Redis 快照，不新增公开 HTTP 接口；快速配桌使用 Colyseus 自带 `/matchmake` 链路。

```text
client/src/composables/useGuestProfile.ts 本机档案凭证、读取与结算后刷新
client/src/composables/useRoom.ts     连接、重连、消息和个人退出

client/src/components/GameTools.vue  顶栏、决策计时提示和返回操作焦点
client/src/components/GameBoard.vue  牌桌、座位、牌组、手牌与操作坞
client/src/components/ActionPanel.vue 合法动作和弃牌确认
server/src/index.ts                   HTTP/Colyseus 启动与辅助接口
server/src/profiles/                  访客档案领域、Redis 持久化与内存降级
server/src/persistence/               活动房快照存储、防抖写入与关停编排
server/src/rooms/GameRoom.ts          房间生命周期、座位和消息路由
server/src/rooms/room-recovery.ts     私有恢复快照格式、版本与校验
server/src/rooms/flow/                牌局状态机、动作执行与结算
server/src/rules/                     牌堆、动作候选、胡牌拆解
server/src/schema/                    公开同步 Schema
```

`GameTools` 由页面层传入 `decisionUntimed`、`decisionSecondsLeft`，并通过 `returnToDecision` 通知牌桌恢复当前操作焦点；这些字段只描述现有服务端决策窗口，不暂停或改写计时。`GameBoard` 接收同一决定状态并持有真实手牌上的弃牌预选、吃牌组合草稿与统一操作坞，打开顶栏弹层不能销毁这些本地交互状态。

触屏手机竖持时，根 `.layout` 负责把物理视口映射为横向有效画布。`useResponsiveViewport` 把 `window.innerWidth/innerHeight` 暴露为随尺寸变化更新的 `--physical-viewport-width/height` 像素变量；根布局在普通方向直接引用它们，自动旋转时交换宽高，再通过 `--effective-viewport-width/height` 向下游组件提供唯一游戏坐标来源。根节点在脚本加载前保留 `100vh` 后备，不能把旧浏览器不认识的 `dvh/dvw` 当作唯一尺寸。设置、记录、确认层和紧凑牌桌的底部手牌操作行都使用上述变量或容器百分比，`GameBoard` 不再直接把物理高度当成游戏高度。牌桌内部三行只能分配实际剩余空间，内容溢出由各牌区自行滚动，牌桌根网格不得产生被 `overflow: hidden` 裁掉的行。显示偏好由根布局统一持久化；游戏内 `reduceMotion` 或操作系统 `prefers-reduced-motion` 任一生效时，根布局对所有子组件统一关闭非必要动画，手牌滚动逻辑同时改用即时行为，不改变服务端状态机时间。

## 8. 当前边界

- 房间 token 与档案 token 都不是生产级账号体系。
- 两类 token 都必须视为秘密；房间 token 可恢复原座并读取私有手牌，档案 token 可读取与更新聚合档案。公网部署必须使用 HTTPS/WSS，邀请链接和日志均不得携带 token。
- 来源限制和基础内存限流只提供轻量边界保护，不代替正式账号鉴权、跨进程限流或专业抗拒绝服务能力。
- 配置 Redis 且保留同一数据卷时，单个服务进程重建可恢复活动房间；未配置 Redis、删除数据卷、格式版本不兼容，或进程与 Redis 同时永久损坏时不能恢复。快照不是跨地域灾备。
- 正式账号、跨设备档案找回、公开房间列表、账号级邀请码和多服务实例之间的房间迁移尚未实现；当前快速配桌只在单个服务进程内聚合玩家。
- 未最终确定的规则不得由旧 SRS 推断，统一记录在 [OPEN_QUESTIONS.md](OPEN_QUESTIONS.md)。
